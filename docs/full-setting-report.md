# 从冻结结果到全设置报告

适用于实验已经结束、原始数据和分析产物已经冻结，用户希望补齐完整报告、比较表和存档索引的工作。目标是让读者能回答主问题、看见全部实际设置，并从一个入口追溯原件；不是再跑一轮实验或重新建立整套归档。

本文是报告层的通用流程。评分/统计契约见 [portable-study.md](portable-study.md)，首次封存、恢复及发布安全见 [efficient-delivery.md](efficient-delivery.md)。现有报告只需定位或解读时，直接回答；只有用户要求整理、更新或生成时才新增报告。发布仍需用户授权及明确目标。

## 1. 计划与验收：先确定要交付什么

沿用已有计划和执行记录，不为本次整理再建立多层审批文件。按数据规模合并步骤；每完成一项，告诉用户产物入口、通过的检查及剩余工作。

| 阶段 | 产物或动作 | 验收标准 |
| --- | --- | --- |
| 冻结输入 | 实际矩阵、显式输入清单、版本与来源 | 能确定分析单元、覆盖范围及每份输入身份，不按得分选文件 |
| 全设置汇总 | 绝对指标、比较、必要的重复层明细 | 所有实际设置均有位置；权重、分母、缺失和差值方向明确 |
| 主问题报告 | 设置、完整表格、结论与资源口径 | 结论可从表中核对，不只展示少数主比较或有利切片 |
| 存档索引 | 原始 dump → 原件清单 → 分片，以及分析附件 | 固定链接可用、范围完整、无误计重复包，大小与哈希来源明确 |
| 成稿核对 | 一次独立数字/逻辑复核、生成器及链接检查 | 修正实际问题；不把作者生成器自检当作独立复核 |
| 授权发布 | 扫描并推送确切增量，核对远端提交 | 保留旧结果，交付报告和索引链接；检查通过后停止 |

这里的验收是**完整、忠实、可追溯**，不是必须观察到 ExpGym 退化或 PoolAct 提升。未完成的实验或缺失数据如实列出；报告整理不自动授权恢复任务、改评分、增加重复或申请 GPU。

## 2. 固定实际设置与输入身份

优先读已发布的 manifest、导出索引、指标和成本账本，而不是递归遍历 raw 目录。确认文件的实际 schema：同名 `manifest.json` 可能是调度计划而非统计预注册；`raw_terminals.csv` 可能只是 agent 终态/评分投影而非 HTTP 请求；oracle 的参考分数也不自动定义指标方向。

记录或引用已有的：

- 数据提交、实际运行的源码/配置/模型/数据/evaluator 身份、评分端点，以及此次分析器/报告版本。后续修补或部署默认值不能反写成历史 run 的设置。
- 分析实际读取的完整文件集合、相对路径、大小、SHA、解释器和必要依赖版本。文件数由真实读取依赖决定，不固定成“八个输入”。不要把回顾性矩阵写成事前预注册。
- 模型 × 场景 × 任务/切片 × 预算 × 策略 × N × 重复/顺序的实际矩阵；区分计划、完成、缺失、未运行。解释 invocation、logical outcome、agent trace 和 pool 的换算。
- 请求生成设置、工具协议、步骤/输出/上下文限制、预算与成本可见性、重复/seed 的解释及本轮服务拓扑。区分请求值与已验证行为、近似 token 与字符数。
- 若有批准的恢复/合并，保留固定槽位的唯一有效来源映射，并另存原失败尝试及成本；不能只保留最终成功项而抹掉历史。

可以复用已有清单和版本证据；输入停止写入后再做汇总。发现身份冲突时只调查受影响输入，不能猜测来源或静默混合不同版本。

## 3. 生成全设置表，而不只生成主比较

以冻结分析契约为准；本仓库常用口径是先在 item 内平均重复，再对 item 等权平均。池内 N 个 agent 的 MI 是一个池级结果，不是 N 次独立重复；Audit 的不同顺序、文档和 hypothesis 也不能相互冒充独立样本。既有导出如果已折叠顺序，不再平均或累计一次。

展示实际存在的 Free / Moderate / Tight，以及各预算下同 N 的 naive / cached / poolact；区分未计划/未运行的组合与计划后缺失/失败的结果，两者均不补零。任务数、N、重复数、模型和切片均从本研究取值，不继承某次案例。跨系统任务子集不同，不能把两个“all”当成同一全集。

表格至少覆盖读者关心的以下层次，规模大时把逐 item 行放机器可读附件：

| 层次 | 内容 |
| --- | --- |
| 绝对值 | 所有实际档位/策略的均值、指标单位、item/repeat 分母；包括 Moderate 和 cached |
| 对照差值 | baseline、target、方向及相同任务/重复范围；常用 cached−naive、poolact−cached、poolact−naive |
| 任务结构 | 预先定义的场景、任务家族和逐任务结果；不因 NAS 某项不利就缩小“all” |
| 重复层 | 实际有重复时给逐 block 值及适当的描述性变动量；R1 不伪造重复层 SD |
| 资源 | 已记录的 token、反馈尝试、模拟反馈成本、真实时长；总成本另用完整账本 |

质量指标中，F1 / EA / LA 的分数差与百分点要区分；Gap 按冻结 oracle/评分定义解释，不因名称把效用误当 regret。保留 MI 与 MV/BoN 的区别，不把已保存的 Gap 重新从汇总 raw 分数反推。展示全部有关指标，不因某一项符合预期而替换原主要端点。

缺失保持 null/unknown，零分保持零。给出 expected/known/missing 分母；已知子集均值单独命名，不冒充完整端点。不要静默取配对交集。seed 标签不证明独立生成，描述 SD 不证明显著性；不因报告润色而静默新增 bootstrap、p 值或更换统计假设。

尽量用一个确定性生成器同时产生 CSV 与展示表。若已有比较表，核对其 baseline/target、分母和方向；新增派生对照另行标明，不覆盖原比较定义。先由未舍入值算差，再格式化。记录数值容差依据；字节重放使用原解释器，不为末位舍入反复换环境或放宽验收来追求通过。

已有分析器仅在 schema/契约适用时复用；不把历史调度 manifest 伪装成 `analyze_portable_study.py` 所需的预注册记录，也不为补一张表重建上游 score audit。

## 4. 围绕主问题写正文

推荐顺序可按用户需求调整：

1. 主问题和实际实验类型；一句说明数据版本及是否新增实验。
2. 完整 setting：矩阵、任务覆盖、N/重复/顺序、预算、生成与评分设置。
3. 预算收紧如何改变表现：展示全部实际档位，说明变化方向和幅度；若退化，发生在哪一段。
4. 共享缓存与协调分别改变什么：同档位、同 N 的绝对值和策略差值；保留任务与 MI/MV/BoN 层次。
5. 资源与时间：质量变化对应哪些已记录的实际开销。
6. 回答主张：方向、幅度、适用任务和模型；表格不支持的部分不写成结论。
7. 完整存档索引、机器可读表、生成方法及有限验收记录。

正文以主问题为主线，不用边界异常清单替代报告。所有正、零、负值保留；足以改变主张的限制放在相应结论附近，其余诊断放附件。汇总层改善不等于每个任务或每次重复都改善，也不自动等于更多模型上同样成立。

资源单位必须读实际 exporter/遥测定义。尤其区分：

- 单 agent、整个 pool 合计与若干顺序的均值；池级 wall 不一定等于 agent wall 的和或最大值。
- 模拟反馈秒与真实推理时长；Free 不必等于反馈成本为零，同反馈预算不等于同 token/GPU 开销。
- reasoning 是否已经包含于 output；完整尝试账本与最终有效结果用量。
- allocation GPU-hours（可能含加载、验证、空闲）与 formal-only 利用量。不能相加并发任务 wall 来推导总历时。

## 5. 把完整存档索引放进报告

正文提供模型/数据集级直接入口，并把完整人读索引和机器索引作为报告附件链接。至少能定位：

- 原始请求/回复/trace 的 collection/bundle 清单、逐原件 member inventory、tar 分片及对应恢复工具。
- 逐 item 指标、全部聚合比较、配对明细、实际矩阵、source index、规范化结果及原始终态投影；以真实文件用途说明角色。
- 全部尝试成本、恢复/合并来源、原分析输出清单和必要的重放环境说明。

数据链接固定提交或不可变发布版本，新报告另有自己的提交身份；不要只给临时绝对路径或会移动的分支链接。文件层索引可引用已有逐原件清单，不必把数十万行重新抄入报告。

区分 bundle 数、tar 分片数、原文件数、原字节和压缩字节；controls、内嵌清单和外层附件的计数范围另说明。按已选归档布局去重物理路径，尤其不要把 composite 引用的旧包再作为额外一整份加入；逻辑来源复用与物理重复副本不要混为一谈。

明确每个 SHA 是继承的已发布声明，还是本次实读核验。检查清单/Git 元数据不等于重新验证 tar 内容，更不等于恢复或重新评分。完整存档还包括外层 CSV/JSON/报告/恢复工具与本次报告；只下载 tar 不足。压缩载荷大小也不等于整个 Git clone 的大小。

旧格式用匹配的恢复器；当前 `package_run.py` 不是所有历史归档的通用读取器。只有用户要完整恢复、格式发生变化或出现具体完整性疑点时，才走相应内容验证/恢复路径。

## 6. 一次成稿复核，增量发布后停止

先完成正文，再做一次独立复核：从冻结输入另算关键聚合和差值、核查矩阵/分母、资源单位、结论与存档范围。可程序化检查全部展示数值；数据量或时间受限时记录实际检查范围，不把抽查称为全量核对。审阅者不只是再次运行作者的 `--check`。

作者侧补充确定性输出复算、schema/链接检查。真实发现只修受影响部分并窄复核；输入、分析代码及结果未变时，不再跑完整模型测试、scorer、raw 解包或整档扫描。一次复核不能宣称“已证明没有任何 bug”。

仅修改报告汇总器/适配器时，用相应 schema/聚合 fixture、确定性复算和成稿核对验证；未改变 runner 或执行依赖，不触发整套 runner/fake integration 测试。仅改文档时检查链接、skill 格式与必要的行为演练即可。

发布时按用户指定仓库、分支和身份操作；文档中的示例不授予 push 权限。沿用 [发布安全流程](efficient-delivery.md)：复用未变旧归档身份，仅扫描确切新增/修改字节，核对 staged 内容与已扫描版本一致，推送后确认远端提交。不要把整个工作目录或未扫描日志顺手加入。

完成后给用户报告和索引的固定链接、覆盖范围、真实检查结果，以及是否推送/合并。验收通过即结束，不继续制造验证记录的验证记录。
